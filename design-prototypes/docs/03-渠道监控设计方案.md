# 渠道监控 · 设计方案（v1）

> 对应原型：`10-user-channel-status.html`（用户端状态页）、`11-admin-monitor-board.html`（管理端主看板，含深色版）
> 现状基础：`frontend/src/views/admin/ChannelMonitorView.vue`、`views/user/ChannelStatusV2View.vue`、`features/channel-monitor-v2/*`（13 个组件）、`docs/channel-monitor-v2-availability.md`

---

## 0. 三个已确认的决策

| 决策 | 结论 | 影响 |
|---|---|---|
| V1 与 V2 的关系 | **合并为一个页面、两个视角**：「真实流量」与「主动探测」，共享时间范围、维度与配置 | 菜单只保留一个入口；V1 从「另一个页面」变成「另一种证据」 |
| 矩阵编码 | **默认 4 档离散状态色**（正常 / 波动 / 异常 / 无样本）；健康分作为连续值**仅在悬停浮层显示** | 保留现有 `health.*` 计算与阈值，只改表现层 |
| 主动探测的定位 | 给**没有客户大量使用**的分组做兜底验证，让客户知道「这个分组现在还能不能用」 | 探测项必须绑定 `group_id`；探测失败只标「探测异常」，不改变「可用」结论 |

---

## 1. 核心模型：一个分组 = 一个结论 + 一个证据来源

这是整个设计的支点。用户问的永远是「我能不能用」，而答案的证据可以来自两条不同的数据通路：

| 证据来源 | 数据来源 | 适用分组 | 时间轴形态 | 结论口径 |
|---|---|---|---|---|
| **真实流量**（V2 被动） | `channel-monitor-v2` 聚合的真实请求 | 有客户使用的分组 | 连续色条（24/48 个时间片） | 可用率 = 1 − 错误率；样本不足不显示数值 |
| **主动探测**（V1 主动） | `channel-monitors` 定时发起的完整请求 | 无客户流量、新上线的分组 | 离散点阵（每次探测一个点） | 最近一次探测通过 / 失败 |

**合并规则（必须严格遵守，否则会误导用户）：**

1. **双重证据时以真实流量为准**。Kimi 企业版这一例：真实流量正常、探测连续 12 次 401 → 结论仍然是「可用」，另加一个灰色 `探测异常` 标记（`border-dashed`，视觉权重低于状态 pill）。
2. **探测失败不是故障**，而是「我们的探测账号可能失效」这类内部问题，属于管理员待办，不属于客户事件。
3. **整体状态横幅只统计有真实流量的分组**。否则一个探测项抖动就会把全站拉红，破坏信任。
4. **样本不足不显示 100%**，显示「数据不足」+ 原因（样本 < N），沿用现有 `health.error_rate === 'unknown'` 的判定。

## 2. 用户端状态页（`10-user-channel-status.html`）

### 2.1 信息架构

```
服务状态
├─ 整体状态横幅        ← 只统计真实流量分组；三项指标：可用率 / 首字延迟 / 进行中事件
├─ 阅读说明（可收起）  ← 一次讲清「真实流量 vs 主动探测」两种证据的含义
├─ 我的分组（按分组，可切按平台）
│   ├─ 真实流量 · 正常
│   ├─ 真实流量 · 波动
│   ├─ 主动探测 · 新上线（带「立即试用」CTA）
│   ├─ 主动探测 · 探测异常（仍是「可用」）
│   └─ 真实流量 · 样本不足
├─ 最近事件（进行中 / 已恢复 / 计划维护）
└─ 说明（口径）
```

### 2.2 分组卡的结构（统一 4 个区域）

| 区域 | 内容 | 设计要点 |
|---|---|---|
| 身份 | 平台色块 + 分组名 + 徽标（如「新上线」） | 平台色沿用的是既定的 6 色，不新增 |
| **证据标签** | `真实流量 · 99.8% · 5 分钟前` / `主动探测 · 401 · 12 分钟前` | **每一种证据一种颜色**：真实流量=主色（teal），主动探测=靛蓝（indigo）。这是全页最重要的识别锚点 |
| 结论 | `可用 / 波动 / 异常 / 可试用 / 数据不足` | 状态 pill，5 档；探测异常另加虚线小标，不改变结论 |
| 时间轴 | 真实流量：连续色条；主动探测：点阵 | 形态本身就是证据类型的第二次提示，不依赖文字 |

### 2.3 「新上线尝鲜」块（转化设计）

针对你提出的转化诉求，单开一种卡样式（左侧 3px 靛蓝边 + 轻渐变底）：

- 徽标「新上线」使用渐变，是全页唯一的强调色，视觉上高于普通 pill；
- CTA 文案是「**立即试用**」而不是「购买」，降低心理门槛；
- 附一句解释「暂时没有其他客户使用，状态来自系统主动探测 —— 可以直接拿来用」，正面回答客户「是不是没人用所以有问题」的疑虑；
- 点击后跳转创建密钥并**预选该分组**，把状态页直接接到转化路径。

### 2.4 与现有实现的差异

| 现状 | 问题 | 提案 |
|---|---|---|
| `/monitor` 按系统模式在 V1、V2 两个视图间二选一 | 用户看到的形态取决于管理员配置，同一个站点体验不一致 | 统一为一个页面，两种证据共存 |
| V1 视图是「渠道卡片 + 弹窗详情」 | 与 V2 的视觉语言完全不同 | 统一为分组卡，只换时间轴形态 |
| 分组以 `group_name` 字符串出现 | 无法和 V2 分组对齐 | 探测项绑定 `group_id`（见 §5） |

## 3. 管理端主看板（`11-admin-monitor-board.html`）

### 3.1 布局（自上而下）

1. **结论条**：`当前 24h：2 个模型降级 · 影响 3.1% 请求 · 主因 上游 529 超载`，右侧直接给两个异常模型 chip + 「只看异常」「查看归因」。目标是把「需要做什么」放在第一屏第一行。
2. **工具栏**：时间范围 → **证据分段控件（真实流量 6 / 主动探测 3 / 全部 9）** → 维度 → 分组 → 刷新 / 监控设置。
3. **主区（左宽右窄）**
   - 左：可用率矩阵（4 档色 + 行尾健康分 pill，悬停浮层给健康分/请求数/TTFT/主因）；
   - 左中：错误率与 TTFT 双线趋势 + 错误分类（按责任方堆叠条）；
   - 右：**错误归因卡** + 主动探测卡 + 下钻入口说明。

### 3.2 矩阵的编码规则

| 维度 | 规则 |
|---|---|
| 颜色 | `≥99%` 绿 / `90–99%` 黄 / `<90%` 红 / 无样本或样本不足 灰（4 档离散） |
| 健康分 | 行尾 pill（≥80 绿 / 50–79 黄 / <50 红），悬停任意色块时浮层显示该片的精确分数 |
| 行序 | 异常行自动置顶，行名后加红点 |
| 列 | 48 个时间片；表头只在 00 / 06 / 12 / 18 / 24 处标注，避免刻度拥挤 |
| 点击 | 打开右侧下钻抽屉（下一张稿） |

> 为什么不直接用健康分的连续色阶：连续色在 20×24 的色块上不可区分，而离散 4 档可以在 1 秒内扫出异常行。健康分保留为「第二层信息」，符合你确认的「默认 4 档、悬停看分数」。

### 3.3 错误归因：解决「上游的问题还是我们的问题」

后端 `ClassifyChannelMonitorV2Error` 是一个**有序首次命中**的分类器，会把错误归到 17 个类别。界面不直接展示 17 类，而是映射为 **4 个责任方**：

| 责任方 | 归并的类别 | 界面语气 | 默认动作 |
|---|---|---|---|
| **上游平台** | `upstream_5xx`、`upstream_forbidden`、`timeout`、`rate_or_capacity` | 「与你方配置无关」 | 查看涉及账号 / 切换备用分组 |
| **我们的账号池** | `authentication`、`quota_or_balance`、`account_pool_unavailable` | 「3 个账号 Token 失效，立即刷新即可消除」 | 跳账号池，**预置筛选条件** |
| **客户端** | `client_cancelled`、`invalid_request`、`context_limit`、`content_policy`、`model_unsupported` | 「不影响可用率，无需处理」 | 无（或一键设为忽略） |
| **平台内部** | `internal`、`group_access`、`not_found`、`transport_or_stream` | 「见 14:22 的 3 条记录」 | 打开请求错误明细 |

每张归因卡固定三段：**占比数字 → 一句话结论（含具体账号/模型名）→ 可执行动作**。管理员不需要自己从百分比里推理。

### 3.4 「忽略影响」预览

现有的「计入可用率 / 已忽略」两栏是好设计，但管理员看不到开关的影响。在归因卡底部加一行：

> 忽略「客户端取消」后的影响：当前可用率 **96.9%** → 忽略后 **99.1%**

让阈值调整的影响**在改动之前**就可见。这是我认为这次最值得加的一个小功能。

| 原型区块 | 数据来源 | 需要改动的代码 |

## 5. 监控设置抽屉（`12-admin-monitor-settings.html`）

已按确认的四条规则落地：

### 5.1 探测项绑定分组

一个分组可以绑定**多个探测项**，因为「同一分组」在现实中可能对应多条不同的上游通路：

| 多探测项的典型来源 | 例子 |
|---|---|
| 不同上游凭据 | 官方直连 KEY-A + 代理通道 KEY-B |
| 不同模型 | deepseek-chat + deepseek-reasoner |
| 检测模式不同 | 一条 `probe` 探活，一条 `quota` 只查额度 |

每条探测项在列表里自带「绑定分组」徽标 + 最近一次结果（通过/失败 + 连续失败次数），并支持运行一次 / 编辑。

**孤儿处理（分组被删除后保留探测项）：**

- 探测项保留，`group_id` 置空，标签变为黄色虚线「未绑定分组」，行尾给出「原分组已被删除…不会出现在用户端」+「重新绑定」按钮；
- 复用现有 `check_mode=quota` 时 `account_id` 被置空的既有先例（「账号删除后被 DB 置空，监控保留并报账号未关联」），提示文案与数据行为保持一致；
- 用户端一律不展示未绑定的探测项，避免归错分组。

### 5.2 多探测项的聚合规则

**已选：任意通过即「可用」**（卡片里给出「已选规则」标记，另两个选项保留为可切换项）：

| 规则 | 语义 | 适用 |
|---|---|---|
| **任意通过即可用（已选）** | 至少一个探测项通过 → 用户看到「可用」，失败项只在详情中列出 | 多通道场景；与「探测失败不降级可用」一致 |
| 全部通过才可用 | 任一失败 → 异常 | 单一可信通路的严格场景 |
| 多数通过才可用 | 通过率 >50% | — |

抽屉里内置一块**实时效果预览**，把当前配置翻译成用户会看到的结论：

> DeepSeek 尝鲜 · 官方直连 通过 / 代理通道 失败 → 用户看到「可用」
> 若切换到「全部通过才可用」→ 用户会看到「探测异常」
> 若两个探测项都失败 → 用户看到「探测异常」

这块的价值在于：管理员改规则前就知道客户会看到什么，不需要上线后靠猜。

### 5.3 判定阈值（12 次可配）

| 字段 | 默认 | 说明 |
|---|---|---|
| 连续失败多少次标记「探测异常」 | **12**（暂定，可配） | 全局默认 + 分组级覆盖 |
| 恢复判定：连续通过多少次 | 2 | 建议约为失败阈值的一半，防抖动 |
| 同一分组多探测项：卡片主项 | **响应最快** | 用户卡片展示延迟最低的一条探测结果 |
| 期望探测间隔 | 300s | 实际执行叠加 ±10% 抖动 |
| 单次探测超时 | 20s | 超时按失败计 |

并自动把「次数 × 间隔」换算成可感知的结论：

> 按每 5 分钟一次、连续 12 次失败计算，一个新上线分组若上游不可用，约 **60 分钟**后才会被标记「探测异常」。若希望更早暴露问题，可把新上线分组的阈值调低到 3–5 次。

这条提示很重要：12 次在 7 天窗口里看很合理，但配合 300s 的探测间隔，意味着**最长一小时才会发现故障**，而新上线分组恰恰是最需要快速暴露问题的。

### 5.4 用户端展示开关

四项开关：展示主动探测分组 / 展示「新上线 · 可试用」入口 / 展示探测时间戳 / 展示分组级阈值（默认关）。
