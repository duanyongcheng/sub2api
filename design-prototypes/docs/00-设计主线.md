# Sub2API 设计主线：一条请求穿过整个系统

> 目的：把前面 13 个原型、3 份文档串成**一条可以讲清楚的链路**。
> 用法：给团队讲设计、给研发排期、给客户解释机制，都可以照着这一条线走。

---

## 0. 为什么需要这条主线

之前每个页面是「点」：工作台、密钥、账号池、分组定价、渠道监控、订单……单独看都对，但放到一起会出现三个问题：

1. **看不出优先级**：44 个页面都重要，等于都不重要。
2. **看不出因果**：账号池一个 Token 失效，为什么客户在遥测页看到的是「上游限流」？
3. **改一个地方不知道影响谁**：把分组倍率从 0.8 调到 0.6，谁的收入变、谁的毛利跌、谁的状态页变成黄色？

这条主线用一个**真实对象**（一次 API 请求）把所有页面串起来：

```
一次请求 → 走哪个分组 → 落在哪个账号 → 扣谁的钱 → 记谁的账 → 出什么事 → 谁看得见
```

每个环节对应一个页面，页面之间用**数据流**而不是菜单层级连接。这也是这套设计最重要的主张：**界面结构应该复刻业务结构**。

## 1. 主链路（七个环节）

```
① 入口            ② 路由             ③ 执行
API 密钥     →     分组与定价    →    账号池
/keys              /admin/groups      /admin/accounts
   │                   │                  │
   │ 归属哪个分组       │ 模型白名单+倍率    │ 粘性会话/优先级/配额
   ▼                   ▼                  ▼
④ 计费            ⑤ 观测             ⑥ 归因
使用记录     ←     渠道监控     ←     运维监控
/usage             /monitor           /admin/ops
   │                   │                  │
   ▼                   ▼                  ▼
⑦ 呈现
用户状态页 / 运营概览 / 订单
```

### ① 入口：API 密钥（`/keys`，原型 02）

**这一环决定什么**：请求以谁的身份进来，受什么限制。

| 字段 | 下游影响 |
|---|---|
| `group_id`（绑定分组） | 决定 ② 走哪条路由——**这是整条链路的分岔点** |
| 额度（金额） | 用完即拒绝，进入 ④ 的「余额不足」记录 |
| 速率限制（5h/1d/7d） | 触发 429，计入 ⑤ 的 `rate_or_capacity` |
| IP 白/黑名单 | 拒绝发生在网关入口，计入运维的「入口拒绝」 |

> **设计要点**：密钥页的「分组」列点击可**行内换组**，这是全站唯一一个会同时改变计费、可用性、可见性的操作，必须给出影响提示。

### ② 路由：分组与定价（`/admin/groups`，原型 05）

**这一环决定什么**：这把密钥能用哪些模型、按什么价扣费、走哪个上游。

- 模型白名单 → 不在名单内直接 `model_unsupported`（客户端责任）
- 分组倍率 / 高峰倍率 / 逐模型定价 → 决定 ④ 的「标准价」
- 复合路由（fallback 链）→ 决定 ③ 的账号候选范围
- 利润控制 → 决定是否触发「成本倒挂」告警

> **设计要点**：定价表上直接显示「毛利 %」，把定价与成本的关系前移到编辑现场，避免事后在运营概览里才发现亏损。

### ③ 执行：账号池（`/admin/accounts`，原型 04）

**这一环决定什么**：这次请求实际落在哪个上游账号上。

- 调度：优先级 + 权重 + 并发上限 + 临时不可调度
- 粘性会话（`stickySessionTTL = 1h`）：同一会话优先复用账号，减少缓存失效
- 失败转移：429/529 自动切换备用账号 → **计入 ⑤ 的「切换次数」**

> **这是整条链路的物理执行点**，账号失效、配额耗尽、代理异常都在这里发生。

### ④ 计费：使用记录（`/usage`，原型 01 的「最近请求」）

每次请求落一条记录：Token 四段、实际费用 / 标准费用、耗时、状态。

- **实际费用**：按分组倍率扣客户的余额或订阅额度
- **标准费用**：按官方价计算，用来体现「省了多少」
- 上游成本：按账号倍率计算，用于 ⑦ 的毛利

> 三者关系：`毛利 = 实际费用 − 上游成本`。这个公式解释了为什么原型 03 的概览页必须把「收入 vs 成本」做成双轴图。

### ⑤ 观测：渠道监控（`/admin/channels/monitor`，原型 11 / 13）

把 ④ 的记录按 `平台 / 分组 / 模型` 聚合，得到可用率。

**归因规则（本套设计的关键一页）**：后端 `ClassifyChannelMonitorV2Error` 的 17 类错误 → 4 个责任方：

| 责任方 | 典型类别 | 指向的下游动作 |
|---|---|---|
| 上游平台 | `upstream_5xx`、`rate_or_capacity`、`timeout` | 切备用分组、暂停调度 |
| **我们的账号池** | `authentication`、`quota_or_balance`、`account_pool_unavailable` | **跳回 ③ 账号池处理** |
| 客户端 | `client_cancelled`、`context_limit`、`invalid_request` | 忽略，不计入可用率 |
| 平台内部 | `internal`、`transport_or_stream` | 跳 ⑥ 运维排障 |

> **这是整条链路最能体现价值的一环**：它把「不可用的现象」还原成「谁的责任 + 去哪个页面修」。

### ⑥ 归因兜底：运维监控（`/admin/ops`，原型 07）

当 ⑤ 的归因是「平台内部」或上游持续异常时，进入运维视角：实时 QPS、延迟分位、错误明细、告警事件、系统日志。

### ⑦ 呈现：三种受众看到三个版本

同一份数据，按受众裁剪：

| 受众 | 页面 | 看到什么 | 不看到什么 |
|---|---|---|---|
| 管理员 | 运营概览（03） | 收入、成本、毛利、待办 | — |
| 管理员 | 渠道监控（11） | 可用率、归因、错误样本 | — |
| **客户** | 服务状态（10） | 我有权限的分组是否可用 + 证据来源 | 账号、上游平台名、内部错误 |

## 2. 三个「贯穿性」设计决策

这三条不是某个页面的事，而是横跨全站的规则。把它们写清楚，比多做三个页面更有价值。

### 2.1 两种证据：真实流量 vs 主动探测

| | 真实流量（V2） | 主动探测（V1） |
|---|---|---|
| 适用 | 有客户使用的分组 | 无客户流量的分组（新上线） |
| 时间轴 | 连续色条 | 离散点阵 |
| 颜色 | 主色 teal | 靛蓝 indigo |
| 多探测项 | — | 任一项通过即可用；卡片主项取**响应最快** |
| 失败处理 | 降低可用率 | 只标「探测异常」，**不改变可用结论** |

> 这套规则的价值：让「新上线但没人用」的分组也能被客户信任，同时不污染真实可用率的统计口径。

### 2.2 状态色板：4 档离散 + 悬停看分数

全站统一：正常（≥99%）/ 波动（90–99%）/ 异常（<90%）/ 无样本（灰）。

- 矩阵用 4 档离散色（可扫读），健康分作为连续值**只在悬停显示**
- 探测异常用**虚线灰标**，视觉权重低于状态 pill——表达「这是内部问题，不是你的问题」

### 2.3 一个分组 = 一个结论 + 一个证据来源

这是 10 号用户状态页的支点，也是 ⑤ 与 ⑦ 的连接点：**管理端的归因结论，直接决定客户看到什么**。

```
账号池 Token 失效（③）
   → 401 authentication（⑤ 归因：我们的账号池）
   → 客户状态页：显示「可用」（因为真实流量被切换到备用账号）✅
   → 管理员待办：去账号池刷新 Token                       ✅
```

而不是：

```
❌ 客户状态页显示「401 错误」 → 客户以为服务挂了 → 客服工单增加
```

## 3. 场景串联：三个真实故事

用具体故事串页面，比架构图更容易讲清楚。

### 故事 A：新客户开通 → 用上 → 省钱

| 步骤 | 页面 | 发生的事情 | 关联数据 |
|---|---|---|---|
| 1 | 登录页（09） | 客户注册并登录 | — |
| 2 | 服务状态（10） | 看到「DeepSeek 尝鲜 · 新上线 · 已通过主动探测」 | 探测项通过 |
| 3 | 点击「立即试用」 | 跳到密钥页并**预选该分组** | `group_id` |
| 4 | 工作台（01） | 看到订阅额度、余额、今日用量 | ④ 的聚合 |
| 5 | 运营概览（03） | 管理员看到该分组新增 1 个客户 | ⑥ 活跃用户 +1 |

**串联点**：10 号的「立即试用」不是营销按钮，而是把 ③ 的探测结果直接变成 ① 的配置。

### 故事 B：上游 429 → 客户无感 → 管理员处理

| 步骤 | 页面 | 观察到什么 |
|---|---|---|
| 1 | 账号池（04） | grok-sso-04 连续 429，被标记降级 |
| 2 | 控制面自动 | 失败转移到 grok-sso-02（切换次数 +1） |
| 3 | 渠道监控（11） | grok-4.1-fast 这一行变黄，错误率 4.2% |
| 4 | 下钻（13） | 归因：**上游平台 · 429 限流占 74%**，与你方配置无关 |
| 5 | 服务状态（10） | 客户看到「波动 · 上游限流，已自动切换备用」——**不会看到 429** |
| 6 | 运营概览（03） | 该分组毛利下降，进入「待办」 |

**串联点**：同一个 429，在 5 个页面里有 5 种正确的说法。这就是「同一份数据按受众裁剪」的价值。

### 故事 C：定价调整 → 影响面

| 步骤 | 页面 | 检查什么 |
|---|---|---|
| 1 | 分组定价（05） | 把 Claude 低价池倍率 0.6 → 0.5 |
| 2 | 定价表内联毛利 | 实时显示毛利从 9.8% → 2.1%，触发红色告警 |
| 3 | 运营概览（03） | 该分组在毛利表中变为「成本倒挂」 |
| 4 | 渠道监控（11） | 该分组请求量可能上升（更便宜） |
| 5 | 客户状态页（10） | **无变化**（价格不影响可用性） |

**串联点**：定价改动的影响面是「收入侧」，不应该污染「可用性侧」——这条要写进研发的验收清单。

> 关键判断：**P1 和 P2 是「必须做」**。P3 已按「只用真实流量」落地，不再依赖 `group_id` 迁移。

### P6 落地说明（边界四态 + 下钻）

| 状态 | 原型 13 号稿要求 | 实现位置 |
|---|---|---|
| ② 首次启用回填中 | 斜纹表示「尚未覆盖」，不能当成 0% 或故障；顶部给进度 | `RelayPulseMatrix` 给每个时间片打 `data-slot-state`，未覆盖用斜纹虚线 + 悬停说明；图例同步；`AdminMonitorBoard` 保留回填进度条。判定口径：色块起点早于 `coverage.coverage_start` 即「尚未覆盖」，晚于则是「无流量」 |
| ③ 刷新时保留旧数据 | 只有手动刷新才出骨架屏，轮询保留旧数据并淡化；右上角显示「正在更新 / 上次成功时间」 | `AdminMonitorBoard` 的 `manual` 标记：骨架屏只在点击刷新时出现；右上角 `monitoring-refreshing` 显示上次成功时间。用户端服务状态页同构 |
| ④ 筛选无结果 vs 真没流量 | 前者给可点的放宽建议，后者说明原因并引导扩大范围 | 两种情况分开文案；有筛选时最多给两条「移除某个条件」，不鼓励一键清空 |
| ⑤ 样本不足不显示 100% | 整行标灰写「样本不足」，不给看起来正常的数值 | P2 已落地，本阶段未改 |

### P7 §5.1 报表导出

| 入口 | 导出内容 | 实现 |
|---|---|---|
| 运营概览「导出报表」（原型 03） | 四张表：汇总 / 趋势 / 分组 / 模型；xlsx 与 csv 二选一 | `features/admin-dashboard/dashboardReport.ts` 纯函数出表，`utils/reportExport.ts` 负责编码与下载 |
| 复盘抽屉「导出复盘」（原型 13） | 单表：覆盖范围 + 指标 + 归因结论 + 每个错误类别的次数/占比/责任方/是否忽略 | `features/channel-monitor-v2/monitorReport.ts` |

三条导出口径，与页面保持一致，不允许离线看表时被重新解读：

1. **口径写进表头**：每张表都有 `口径` 列说明「实际收入 = 按分组倍率扣费」「毛利 = 实际 − 上游成本」「毛利率 = 毛利 ÷ 实际收入」。
2. **未知不写 0**：样本不足写「数据不足」，历史未覆盖写「部分覆盖（回填中）」；分组缺 `account_cost` 时毛利与毛利率都写「数据不足」，而不是 0（0 会被读成 100% 毛利）。
3. **空范围不导出**：当前范围没有任何数据时给提示，不生成空白文件。

技术备注：CSV 带 BOM 并对 `= + - @` 开头的单元格做公式注入防护；xlsx 走动态 `import('xlsx')`，不进首屏包；文件名为 `<报表>_<起>_to_<止>`，复盘用 `2026-11-08_1400` 这种可读的时间窗。

### P7 §5.2 订单三页合并

原型 08 的「订单」是一页:概览在上、列表在下、退款是弹窗。落地时保留了原有
三个页面的能力，改为**一个路由 + 三个 Tab**：

| Tab | 原页面 | 说明 |
|---|---|---|
| 概览 | `/admin/orders/dashboard` | 每日收入、支付方式分布、消费排行 |
| 全部订单 | `/admin/orders` | 筛选 + 列表 + 行内退款 / 重试 / 取消 |
| 套餐 | `/admin/orders/plans` | 订阅套餐 CRUD、上架开关 |

三条实现约定：

1. **旧路径不失效**：`/admin/orders/dashboard`、`/admin/orders/plans`、`/admin/orders/list`
   全部重定向到 `/admin/orders?tab=…`。菜单省下一项，但书签和外部链接照旧能用。
2. **Tab 懒挂载、只加载一次**：切换用 `v-show` 保留筛选与滚动位置；每个面板第一次
   显示时才挂载并 `init()`，之后切回不重复请求，避免「点一下就白跑一次接口」。
3. **待办置顶用真实计数**：「已支付未到账」与「退款申请」两张卡片的数字来自
   `GET /admin/payment/orders?status=…&page_size=1` 的 `total`，点进去直接预置该状态；
   计数失败时整条不显示，不展示猜测值。

**下钻抽屉（`MonitorDrilldownDrawer`）**：概览页签新增「归因结论」区块——责任方 pill + 一句话结论（含占比与主要类别）+ 最多四个动作（查看涉及账号 / 去运维监控 / 设为忽略类别 / 复制错误样本）。动作只在数据支持时出现：账号池动作要求筛选里恰好一个平台，内部责任方动作携带 `open_error_details=1` 深链到运维监控。样本不足时直接说「不给出归因结论」，不猜。

### 关于「两种证据合并」的决策记录

原型 10 号稿原设想在同一张分组卡上并列「真实流量 + 主动探测」两种证据。该方案**已放弃**，原因：

1. 合并的前提是探测项能稳定对应到分组，而 `channel_monitors` 只有自由填写的 `group_name`，没有 `group_id`；按名字匹配会在分组改名、重名、留空时错绑，而错绑比不绑更危险。
2. 更根本的是**运营形态**：V1 探测与 V2 真实流量是互斥的系统模式，现实中不存在「同一分组既有真实流量、又挂探测兜底」的需求。为一个用不上的组合关系改数据库没有必要。

因此用户端 `/monitor` 改为**只呈现真实流量**：整体状态横幅 + 按分组的结论卡 + 时间轴 + 模型明细。探测结果仅保留在管理端「主动探测」列表，并在列表上标注「未绑定分组」，明确它不参与任何用户可见结论。

> 若未来确实需要合并：不要给 `channel_monitors` 加一列 `group_id`，而应新增 `group_probe_bindings` 关联表——设计允许「一个分组绑定多个探测项」，一列无法表达，且删分组时关联行可级联清理，探测项本身保留。

## 7. 一页话总结

> **把这套设计记成一句话**：
> 一次请求从密钥出发，经分组定价决定「按什么价走哪条路」，在账号池落地执行，产生计费与可用率两类数据；
> 可用率被归因成「谁的责任」，再按受众裁剪成三个版本——管理员看毛利与待办，运维看错误与告警，客户只看到「我能不能用」以及**凭什么这么说**。
>
> 界面之所以这样组织，是因为业务的连接方式本来就长这样。
