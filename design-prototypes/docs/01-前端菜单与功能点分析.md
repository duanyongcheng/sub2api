# Sub2API 前端菜单与功能点分析

> 分析对象：`frontend/`（Vue 3.5 + Vue Router 4 + Pinia + Tailwind 3，Vite 构建）
> 后端路由：`backend/internal/server/routes/{admin,auth,user,payment,gateway}.go`
> 分析基线：commit `d55dcdf94`
> 结论一句话：**这是一个「AI API 网关 + 额度分发 + 商业化」三合一的平台**。前端按角色（游客 / 用户 / 管理员）分三套外壳，菜单本身只有 3 类：用户自助 12 项、管理员后台 22 项（含 6 个二级分组）、以及公开页。

> **📌 先看** [`00-设计主线.md`](00-设计主线.md)：本文是全站菜单与功能点的**静态盘点**，主线文档解释这些页面**如何串成一条业务链路**（入口→路由→执行→计费→观测→归因→呈现）。

### 1.4 Header（全局操作区）

`公告铃铛（红点未读数）` · `文档链接` · `模型广场` · `语言切换(zh/en)` · `订阅进度胶囊` · `余额胶囊（可用/冻结/总计，hover 展开）` · `用户下拉（个人资料、API 密钥、GitHub、客服联系方式、重玩新手引导、退出）`

### 1.5 路由守卫里的 5 类动态拦截（做原型时决定「菜单是否出现」的真相）

1. **功能开关**：`payment_enabled / risk_control_enabled / subscription_enabled` 为 `false` → 重定向。
2. **模型广场**：`model_plaza_enabled=false` 拦截；`model_plaza_require_auth=true` 未登录跳登录。
3. **简易模式**：4 条路径（订阅、兑换的管理端和用户端）硬拦截。
4. **后端专用模式（backend mode）**：非管理员登录后只能看到登录页白名单。
5. **合规弹窗**：管理员首次进入需 `POST /admin/compliance/accept`（423 拦截）。

## 2. 功能点清单（按模块）

标注：`★` 高频主路径 · `⚙` 配置型 · `⚠` 高危操作（需二次确认 / step-up）

### 2.1 身份与账户（auth）

| 功能点 | 交互要点 | 接口 |
|---|---|---|
| ★ 邮箱密码登录 | 记住我、错误码映射（`USER_NOT_ACTIVE`）、条款勾选 | `POST /auth/login` |
| ★ TOTP 二次验证 | 登录后进入 2FA 步骤，支持邮件验证码方式 | `POST /auth/login/2fa` |
| ★ Passkey 登录 | WebAuthn，按钮级 loading | `POST /auth/passkey/login/{begin,finish}` |
| ★ 注册 | 邮箱后缀白名单、域名限流提示、邀请码/优惠码校验、Turnstile 人机验证 | `POST /auth/register`、`/auth/validate-{promo,invitation}-code` |
| ★ OAuth 登录 | LinuxDo / GitHub / Google / 微信 / 钉钉 / 通用 OIDC，6 套回调页，未绑定邮箱时走「补邮箱」分支 | `/auth/oauth/*/start`、`/auth/oauth/pending/*` |
| 忘记/重置密码 | 邮件链接 | `/auth/forgot-password`、`/reset-password` |
| ⚙ 个人资料 | 昵称/头像、改密码、通知邮箱绑定（发码→验证→开关）、第三方账号绑定/解绑、平台配额查看 | `/user/profile`、`/user/notify-email/*`、`/user/account-bindings/*` |
| ⚙ 安全设置 | TOTP 开关、Passkey 列表/重命名/删除、敏感操作 step-up | `/user/totp/*`、`/user/passkeys` |
| ⚙ 自定义页面 | 后台配置的富文本/Markdown 页面（`marked` + `dompurify`） | `/custom/:id` |

## 4. 现有 UI 的问题（这次重设计的立足点）

1. **信息密度失衡**：44 个页面里，`GroupsView` 6942 行、`SettingsView` 13394 行，而用户端最常用的「密钥」页功能塞满了 1 个屏幕宽的表头（搜索 + 2 个筛选 + 端点提示 + 批量条 + 刷新 + 列设置 + 新建）。
2. **导航层级不表达业务模型**：管理员 22 项平铺，没有按「流量（账号/分组/渠道）× 客户（用户/订阅/订单）× 安全 × 系统」分组；渠道管理只有 2 个子项却占一个折叠组，而账号管理（60+ 接口）是单入口。
3. **状态语言不统一**：`StatusBadge` 用绿/黄/红圆点，账号/订阅/订单/监控 4 种状态机各写各的徽标。
4. **缺少「一眼可判」的运营视图**：仪表盘 8 个卡片 + 2 图 + 2 表，但**成本 vs 收入**（实际 vs 标准）这个核心业务指标被塞在卡片副标题里；运维页 20 多个子组件、单页 865 行，且告警、错误、日志三类「需要行动」的信息分散在页面下部。
5. **深色模式是事后叠加**：大量 `bg-xxx-100 dark:bg-xxx-900/30` 手写旁路。
6. **安全审计四页功能重叠**：操作日志、内容审计、提示词审计、运维告警都在做「记录 + 通知 + 封禁/静默」，交互各不相同。

## 5. 重设计方向（承接第 4 节）

| 方向 | 具体做法 |
|---|---|
| **导航三分区** | 流量（账号/分组/渠道/监控）· 客户（用户/订阅/订单/支付/兑换/返利）· 系统（安全/日志/设置/插件/备份）。二级菜单用「图标 + 计数徽标」 |
| **一屏一决策** | 每个列表页顶部只放 3 件事：**主指标带**（4 个 KPI）、**搜索 + 智能筛选 chips**、**主操作**；次要操作收进 `⋯` 与「视图」菜单 |
| **状态色板** | 定义 5 档语义色（正常/警告/危险/进行中/停用）+ 统一 pill 组件，账号健康度用「信号灯 + 百分比」 |
| **运营中枢** | 仪表盘改为「收入-成本」双轴图 + 异常卡片（异常账号数、失败率突增、待处理订单），把「需要行动」放最上层 |
| **表格即工作台** | 行高 56、首列粘性、行内 hover 才出现操作、右侧详情抽屉（Drawer）替代 90% 的模态框 |
| **密度切换** | 提供「舒适 / 紧凑」两档密度，管理员默认紧凑 |
